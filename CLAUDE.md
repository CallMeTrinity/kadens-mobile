@AGENTS.md

## Project

Kadens Mobile: a live workout-tracking Android app for [Kadens](https://kadens.antoninpamart.fr). It runs a scheduled
workout, logs what was actually done set by set, and does this **offline**, syncing later. The Symfony server lives
in a sibling repo (`kadens`); the full spec, decisions, and tickets are in `kadens/docs/feature-live-tracking.md`,
and the API contract is in `kadens/docs/api-mobile.md`. Android only — no iOS tickets, no iOS build is verified.
Distributed via a self-hosted F-Droid repo, not the Play Store.

Stack: Expo SDK 57 (React Native 0.86), TypeScript, `expo-router`, Drizzle ORM over `expo-sqlite`.

## Commands

```bash
npm install
cp .env.example .env          # then set the LAN IP, see below

npm start                     # adb reverse + expo start --localhost; scan the QR with Expo Go
npm run android                # adb reverse + expo run:android on the connected device/emulator
npm run web                    # react-native-web render; dev convenience only, nothing is verified there

npm run lint                   # ESLint (eslint-config-expo + Prettier)
npm run format                 # Prettier, writes
npm run format:check           # Prettier, read-only — what CI runs
npm run typecheck              # tsc --noEmit

npm test                       # Jest (jest-expo/android preset)
npm run test:watch             # same, in watch mode

npm run db:generate            # drizzle-kit generate — regenerate src/db/migrations/ from schema.ts

npm run sync:tokens            # design-tokens.json -> src/theme/tokens.ts (generated)
npm run sync:fonts             # public/fonts/*.ttf -> assets/fonts/
npm run sync:icons             # public/pwa/android/*.png -> assets/images/
npm run sync:design            # all three of the above
```

Verification is `typecheck` + `lint` + `format:check` + `test`, all four run by CI on every push
(`.github/workflows/ci.yml`), plus a manual run on Android — nothing here renders a screen on a device.

### Developing against a local Symfony backend

The phone is not the machine: `localhost` in `EXPO_PUBLIC_API_URL` resolves to the phone itself and fails silently
(looks like a network outage, not a config error).

1. Get the machine's LAN IP: `ipconfig getifaddr en0` (macOS Wi-Fi).
2. Start Symfony listening on all interfaces (it defaults to loopback only): `symfony serve --listen-ip=0.0.0.0 --port=8000`.
3. Set `EXPO_PUBLIC_API_URL=http://<that-ip>:8000` in `.env`.
4. Machine and phone must be on the same network, without Wi-Fi client isolation.

`EXPO_PUBLIC_API_URL` is only a dev default — in real use, the pairing QR shown in `/profile/settings` carries the
server URL and configures it in the process (KL-48).

### Native modules and the `android/` folder

`android/` is **not versioned** — it's regenerated by `expo prebuild` as part of the build workflow. Any native
config (permissions, signing, intent filters) goes through a plugin declared in `app.json`; a hand edit under
`android/` is silently wiped on the next build.

Adding a native module requires a rebuild, not just a reload: the dev build (`expo-dev-client`) has its native
module set frozen at compile time. Metro still rebundles JS on save, so new code reaches the phone, but a missing
native module fails as `Cannot find native module 'Expo...'` followed by a cascade of "Route is missing the
required default export" — nothing wrong in the code, just run `npm run android` again. After `npx expo install
<module>`, always rebuild.

## Architecture

### One entry point per module — always import from the barrel

Every top-level module under `src/` (`@/api`, `@/db`, `@/theme`, `@/components`, `@/session`, `@/sync`) exports
everything through its `index.ts`. Screens and services import from `@/api`, never from `@/api/endpoints` directly
— this is a deliberate, enforced convention, not incidental structure, so a file inside a module can be split or
renamed without touching call sites. Each `index.ts` carries a substantial doc comment explaining the module's
invariants; read it before working in that module, it usually answers the "why is this built this way" question
before you have to ask it.

The path alias `@/` points at `src/`.

### Layered structure and where logic belongs

```
src/
  app/          expo-router routes (one route = one file)
    (tabs)/     the three bottom-nav destinations, sharing one stack entry
    session/    a live workout — stacked ABOVE the tab bar, deliberately
  api/          HTTP client, typed endpoints, session and token
  db/           local SQLite: schema, migrations (generated), queries live in @/session instead
  session/      the live-workout domain: starting/logging/deviating a workout
  sync/         the sync engine gluing @/api and @/db together
  components/   base components (Button, Field, Sheet…)
  theme/        generated tokens, typography scale, fonts
  config.ts     env-derived configuration
tools/          scripts that sync design tokens/fonts from the server repo
```

`@/db` knows how to write rows; `@/api` knows how to talk to the server; neither knows what "starting a workout"
means (that a closed workout can't be resumed, that a freeform workout is born at today's date with a
locally-minted uuid, etc.) — that domain logic lives in `@/session`, not in a screen. `@/sync` is the only module
where `@/api` and `@/db` meet durably (the root layout also crosses them briefly, to restore the URL and token at
startup) — the HTTP client never opens SQLite, the DB never calls the network.

### Local DB: prescribed is a document, logged is normalized

The local SQLite schema (`src/db/schema.ts`, extensively commented — read it before modifying) mirrors
`GET /api/bootstrap`. Three decisions shape it:

1. **Prescribed data is one JSON document per workout** (`prescribedSnapshot.blocks`), replaced wholesale on every
   pull — never recomposed on the phone ("in a workout you deviate, you don't rebuild"). **Logged data is
   normalized** (`loggedExercise`, `loggedSet`) because it's written set by set during a live workout, is the only
   part of the DB the phone mutates, and needs indexing.
2. **IDs aren't reinvented.** `exercise.id` is the server's sequential ID. `scheduledWorkout.uuid` and
   `loggedSet.uuid` are client-minted UUIDv7s (`db/uuid.ts`) — this is what makes `PUT /api/schedule/{uuid}`
   idempotent. Only `loggedExercise` and `mutationQueue`, which the server never addresses by ID, get a local
   autoincrement key.
3. **Timestamps are ISO 8601 UTC text, always `…Z`**, never epoch integers — matches what the API sends/accepts and
   avoids timezone loss. The server misreads a non-null offset as if wall-clock time were UTC.

There's no "modified locally" flag on `scheduledWorkout` — that fact is already carried by `mutationQueue` (a
pending workout has a row there). This is why push-before-pull is non-negotiable (see below): two sources for the
same fact would eventually disagree.

### Exercise names: two labels stored, one place that picks (`src/session/naming.ts`)

An exercise carries a French name and an optional English one (`nameEn`, null when the French name _is_ the
English one — "Dips", "Fartlek"), and the **account** says which to read (`syncState.exerciseLanguage`, pulled with
the library it governs). `naming.ts` is the mobile twin of the server's `ExerciseNaming`, and the same rule holds:
a component that writes `row.name` bypasses the preference.

- **Both labels are stored, never just the current one.** `?since` only slims the library; keeping the resolved
  label would freeze every row a delta doesn't re-send in the old language.
- **The living name wins over the frozen copy.** The program and the log each carry a name (French by
  construction — one is the live name at pull time, the other a snapshot taken during the workout). The session
  re-resolves through `exerciseId` against the local library and only falls back to the transported name when the
  exercise has left it. Renaming an exercise therefore renames it in history — same accepted consequence as the web.
- **What gets frozen takes the canonical name.** `loggedExercise.exerciseName` is written from the library row
  (`libraryReference`), never from the displayed label: a snapshot carries one language and it travels to the
  server.
- **Search reads both names, sorting reads the displayed one.** `toOptions()` resolves label, search text and
  order in one pass, per language change — not per keystroke.
- The preference is **read-only here** (shown in the settings "Compte" card); it is set in the web app's
  `/profile/settings`.

### Sync engine: push always before pull, one cycle at a time

`syncNow(trigger)` in `src/sync/engine.ts` (also extensively commented) never throws and never blocks the UI —
triggers (app launch, foreground, network back, workout closed, manual) have no one to catch an exception, so the
engine publishes a status (`useSyncStatus()`) and screens read the local DB, which republishes live reads via
`enableChangeListener` when a pull writes.

- **Push before pull, always.** Pull _replaces_ the scheduled-workout window; pulling first would wipe out a
  workout finished this morning but not yet pushed. There is no exposed "pull only" path.
- **One cycle at a time.** A request that arrives mid-cycle isn't dropped or doubled — it's queued and the running
  cycle chains a second one at the end.
- **A workout with a pending mutation is untouchable by pull** — the local DB stays authoritative for it until the
  server confirms.
- Logging a set means enqueuing a mutation (`enqueueSchedulePut`) **in the same transaction** as the write — an app
  killed between the two would otherwise leave logged data silently unpushed.

### Driver quirks worth knowing before writing DB code (`src/db/client.ts`, `src/db/index.ts`)

- The Drizzle/`expo-sqlite` driver is synchronous. `db.transaction()` commits as soon as its callback _returns_ —
  an `async` callback would commit before the first write actually lands. Inside a transaction: non-`async`
  callback, explicit `.run()` / `.get()` / `.all()`.
- A `DELETE` that clears an entire table must carry a `WHERE` clause. Without one, SQLite's truncate optimization
  skips `sqlite3_update_hook`, so `useLiveQuery`-backed views silently stay stale. See `wipe()` in `db/seed.ts`.
- `PRAGMA journal_mode = WAL` and `PRAGMA foreign_keys = ON` are set on every open (SQLite disables FK enforcement
  by default, per-connection) — without the latter, `ON DELETE CASCADE` would be decorative and deleting a workout
  would silently orphan its logged data.

### API client rules (`src/api/index.ts`, extensively commented)

- The token lives only in `expo-secure-store`; the transport sets it, no screen reads/passes/logs it.
- A `401` purges the session and the navigation guard in `src/app/_layout.tsx` (via `Stack.Protected` +
  `useSession()`) switches to the login screen — nothing to intercept in a screen for this.
- `GET`/`PUT`/`DELETE` are retried on transient failure, `POST` is not (a replayed `login` would mint a second
  token nobody holds).
- Failures are typed (`NetworkError`, `TimeoutError`, `ApiError`, `ConfigurationError`) and inspected via
  `isTransient()` — never by parsing the error message/`detail`.

### Degraded states: one writer for failure text, one banner, one boundary (KL-38)

- **`describeError()` is the only thing that writes a failure sentence.** A screen never composes its own, and
  never renders `error.message` — that string is written for the console (library English, method and path) and
  must not reach someone mid-workout. Nothing it returns carries an HTTP code, a method or a path: the server's
  `detail` comes first (the contract guarantees French, meant to be read), a status table takes over when there
  is none, and a `422` speaks through its first `violation`. A test walks twelve statuses to keep it that way.
- **Offline is the nominal state, not a fault.** The banner is mounted once, in `app/(tabs)/_layout.tsx`, above
  the tab bar — never in a live workout. It reads `useOfflineNotice()` (`@/sync`), which crosses the phone's
  network state with the engine's `offline` flag because "no network" and "server not answering" don't get fixed
  the same way. Secondary ink, no red, no target, `accessibilityLiveRegion="polite"`.
- **A white screen is impossible.** `app/_layout.tsx` exports an `ErrorBoundary`; errors from any route climb to
  it. Its exit doors are `retry()` and a fallback that navigates home _before_ re-arming (retrying in place
  replays the same error). It renders `Fault`, shared with the migrations guard.
- **Every list has a drawn empty state** (`EmptyState`, `compact` inside a sheet/section/card). Two exceptions are
  deliberate and documented in the ticket: the settings queue says its emptiness in its summary row, and a missing
  exercise history is "first time", not an empty list.

### Gym ergonomics: one primary target, at the bottom, always (KL-39)

The use context is standing, one-handed, greasy screen, sometimes in the dark. Four rules fall out of it, and
none of them is cosmetic.

- **The live workout's only primary action lives in `SessionDock`**, pinned to the bottom of the screen. It
  stacks the rest strip (when one runs) and then the **validate row, always last** — so the main target sits at
  a constant distance from the edge whether resting or not. A workout that hasn't started yet shows one button
  there and nothing else ("Démarrer la séance"): the screen is now reachable **without** starting, since Today's
  card splits into "Voir la séance" + a small "Démarrer", and the thumb shouldn't relearn a position between
  opening the workout and logging its first set. It offers `nextTarget()` (`@/session`, pure and
  tested): the first checkable set in reading order, except inside a superset, where members **alternate** by
  fewest logged sets. No target left means the row becomes the close button, which is why the in-flow "Terminer
  la séance" button is `secondary` — one primary per screen. Set rows stay individually tappable; the dock is
  the short path, not a replacement for reading the table.
- **The current set is never lost**: it's written in the dock, and the scroll view catches up to it via
  `useRevealTarget` when the current _exercise_ changes (never between two sets of the same one — a screen that
  re-centres under your thumb is worse than the problem). Measurement is `measureInWindow` on the target and on
  the scroll frame, not a sum of nested `onLayout` offsets.
- **Colour carries an AA floor, and two rules enforce it.** Faint ink (`textFaint`) carries **no text anywhere**
  — it fails on paper (3.4:1) and on `fill` (4.2:1), and a token whose validity depends on the surface it lands
  on is a trap. Red that is **written** is `primaryOnTint`; full `primary`/`statusMissed` stay for fills, dots
  and rules, where 3:1 is the bar. `src/theme/__tests__/contrast.test.ts` holds the declared ink/surface pairs
  and derives each threshold from the **typographic role** — a new pair is added by hand when introduced.
- **Motion and keyboard are measured, not assumed.** `useReducedMotion()` (`@/theme`) gates the only two
  movements in the app (a sheet rising, the reveal scroll). `useKeyboardOverlap()` (`@/components`) returns
  `host height − keyboard top`, not the keyboard height: an Android window may resize under the keyboard or
  not, and the same formula is right either way. Where it applies, the bottom safe-area inset **stops being
  added** — the keyboard already covers the gesture bar.

### Tests run against a real SQLite and a real API client (KL-36)

Suites live in `src/**/__tests__/*.test.ts(x)`, helpers in `src/test/` (excluded from `testMatch`). Two decisions
shape everything and are worth knowing before writing a test:

- **`expo-sqlite` is replaced by `node:sqlite`**, not by a stub (`__mocks__/expo-sqlite.ts`, applied automatically
  by Jest to every importer). What the tests verify _is_ SQLite: a transaction rolling back, `ON DELETE CASCADE`,
  `AUTOINCREMENT` not reusing a freed rank. The schema comes from the repo's own migrations (`src/test/database.ts`),
  never from a copy that would drift on the next `npm run db:generate`. `resetDatabase()` in `beforeEach` — the
  connection is opened once at module load and is not replaced.
- **Only `fetch` is stubbed** (`src/test/http.ts`), so all of `src/api` stays in the loop: timeout, retry, `201` vs
  `200`, the error taxonomy. Mocking the endpoints instead would test the mocks. The default `fetch` **fails**,
  naming the call: `@/session` writes must never touch the network, and that guard is what proves it.

Fixtures build API payloads and seed the DB by applying a real pull (`src/test/fixtures.ts`), so no test sets up
state through a path the app doesn't use. Note `@testing-library/react-native` v14: `render` and `fireEvent` are
**async** — forgetting the `await` yields an empty `screen`, not a failed assertion.

### Navigation: three tab destinations, a live workout on top of them

`src/app/(tabs)/` holds History, Today and Settings — in that order, chronological rather than hierarchical,
with the app's default destination in the **centre**, the safest spot for a thumb on a three-target bar. The
order is `TabList` child order only; the navigator's initial route still comes from the file system (`index`).
They sit behind a hand-drawn bar built on the **headless**
`expo-router/ui` components (`Tabs`/`TabList`/`TabTrigger`/`TabSlot`) — the classic `<Tabs>` navigator
configures a bar, it doesn't let you draw one, and the Presse identity is not a configuration. A live
workout (`session/[uuid]/…`) is a `Stack` screen **above** the group, not a tab: it runs full-screen and
must not give thumb space to three tabs instead of "validate this set". A group doesn't appear in the
URL — `/settings` is still `/settings`.

**Safe areas** (Android is edge-to-edge since SDK 54, nothing is reserved). The top is settled once, by
`Header`. The bottom is per-screen, and there are two cases that don't render the same way: a bar painted
at the bottom takes the inset as **padding** (it paints under the gesture bar, its targets move up); a
scrolling page adds it to its content `paddingBottom`. Never both on the same screen — see the doc
comment in `src/components/Header.tsx`.

### Design tokens are generated, never hand-edited

Design identity comes from the server (`kadens/public`), not this repo. `src/theme/tokens.ts` is generated by
`npm run sync:tokens` and versioned — editing it by hand is a wasted edit, regenerate instead. A value React
Native can't express (`color-mix()`, a font stack, a non-zero mixed radius) fails the sync command rather than
being approximated. The type scale is _not_ part of the tokens (the web side expresses it with `clamp()`); it
lives hand-written in `src/theme/typography.ts`, along with the casing rule: structural labels in Barlow Condensed
caps, user-entered content in normal-case Barlow. There is no dark theme — the visual identity is paper-and-ink,
so there's exactly one set of values and no `useColorScheme` anywhere in the app.

The app's **visuals** (`assets/images/`) are generated the same way, by `tools/build-pwa-icons.php` in the
server repo, and pulled in by `npm run sync:icons`. Their source is `assets/icons/kadens-red-black.png`, the
red-and-black variant of the mark — **deliberately not the site's logo**, so the two don't blur together on a
home screen. It ships already cropped to the K on an opaque white matte, so there is nothing to isolate and
everything to key out. They're transparent except `icon.png`: on Android the
background colour is _declared_ (`adaptiveIcon.backgroundColor`, `expo-splash-screen.backgroundColor`) and
composited at display time, so baking one into the image would hide the declared layer — that was the bug in
the hand-copied PWA icons this replaced. Every filename is also declared in `app.json`; renaming one there
without the other breaks `expo prebuild` on a missing path.

**Icons** are Lucide, frozen locally in `src/components/Icon.tsx` (`react-native-svg`), copied verbatim from
the server repo's own frozen set in `assets/icons/lucide/` — a `git grep calendar-days` across both repos must
land on the same drawing. A new icon is imported server-side first
(`php bin/console ux:icons:import lucide:<name>`), then transcribed.

**Red means one of three things** and nothing else: a primary action, intensity, failure. Categories
(activity, target area, block role) are coded by their **rank in the grey scale** (`colors.cat1…cat4`), never
by an invented hue. Failure is `colors.statusMissed`, not `colors.primary` — they share a value today, not a
meaning, and the web uses `--color-status-missed` on `.kd-flash--error`.
